Actúa como Principal Ledger Core Engineer y CPA Systems Auditor.

PROBLEMA CRÍTICO:
Por décima vez, cuando el usuario borra/anula un pago, gasto, cargo o asiento erróneo, la UI parece borrarlo, pero contablemente sigue vivo. Sigue afectando:
- Cash Clearing
- pagos registrados
- pagos al capitán
- cuentas por pagar
- gastos
- profit
- reconciliation
- reportes

YA NO QUIERO MÁS PARCHES DE UI.

SOLUCIÓN OBLIGATORIA:
Crear un único motor central llamado:

voidAccountingSource()

Todos los botones de borrar/anular deben usar ese motor. Ningún módulo puede borrar o esconder registros por su cuenta.

==================================================
1. REGLA ABSOLUTA
==================================================

Prohibido:
- DELETE físico contable
- ocultar en frontend sin afectar ledger
- cambiar status visual sin reverso
- recalcular localmente en UI

Obligatorio:
- crear reversal contable
- marcar source original como voided
- marcar source original excluded_from_ledger=true
- recalcular desde backend
- refrescar UI desde GET /reconciliation
- dejar audit trail

==================================================
2. CREAR FUNCIÓN CENTRAL
==================================================

Crear en backend:

async function voidAccountingSource({
  source_type,
  source_id,
  booking_id,
  reason,
  voided_by
})

Debe soportar:
- booking_payment
- booking_expense
- captain_payment
- captain_payable
- booking_payable
- booking_payable_payment
- corporate_expense
- corporate_payable
- corporate_payable_payment
- other_income
- revenue_recognition
- manual_entry
- transaction
- journal_entry

==================================================
3. QUÉ DEBE HACER
==================================================

La función debe:

1. Validar reason obligatorio.
2. Buscar el source real en su tabla.
3. Verificar si ya está voided/reversed.
   Si sí:
   devolver HTTP 409 ALREADY_VOIDED.
4. Buscar todas las transacciones/journal entries relacionadas.
5. Crear asiento reverso exacto:
   - debit original se vuelve credit
   - credit original se vuelve debit
6. Marcar registros originales:
   status='voided'
   excluded_from_ledger=true
   voided_at
   voided_by
   void_reason
   reversal_journal_entry_id
7. Marcar journal/transactions originales:
   status='reversed'
   is_reversed=true
   excluded_from_ledger=true
8. Actualizar saldos derivados:
   - total_collected
   - total_expenses
   - cash_clearing
   - captain_paid
   - payable_balance
   - AR
   - profit
9. Guardar audit log before/after.
10. Devolver ledger actualizado.
