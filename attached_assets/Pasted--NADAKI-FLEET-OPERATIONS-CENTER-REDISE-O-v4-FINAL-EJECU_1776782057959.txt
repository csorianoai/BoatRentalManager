# NADAKI FLEET OPERATIONS CENTER — REDISEÑO v4 (FINAL EJECUTABLE)

## Contexto y misión

El calendario actual de /dashboard.html (grid semanal horizontal con bloques verdes) es funcional pero operativamente pobre. No responde las preguntas que un operador de flota se hace al abrir el sistema.

Reconstrucción completa hacia lo que internamente llamaremos Nadaki Fleet Operations Center — un Operations Command Surface que permita responder en menos de 10 segundos:

1. ¿Qué barcos están ocupados AHORA?
2. ¿Qué salidas vienen HOY?
3. ¿Qué huecos vendibles existen esta semana?
4. ¿Qué reservas están en RIESGO (pago pendiente, tripulación faltante, conflicto)?
5. ¿Qué barco está subutilizado?
6. ¿Quién es capitán/stew de cada salida?
7. ¿Cuánto se factura por día/semana/barco?
8. ¿Hay conflictos de tripulación o overbooking?

No es un rediseño visual. Es la transformación de "booking calendar" a "fleet operations calendar".

## FILOSOFÍA Y PILARES

El sistema descansa en 5 pilares:
1. Visualización de flota — ver toda la flota en un solo vistazo
2. Operación diaria — coordinar tripulación, horarios, logística
3. Alertas accionables — detectar riesgos antes de que escalen
4. Rentabilidad integrada — revenue y utilización visibles en cada vista
5. Detección de gaps y conflictos — huecos monetizables y solapamientos

## MODELO MENTAL — 4 CAPAS DE INFORMACIÓN

- Capa A Planificación: reservas, holds, maintenance, buffers, disponibilidad
- Capa B Operación: capitán, stew, check-in, boarding, departure, retorno
- Capa C Rentabilidad: revenue por salida, revenue del rango, ocupación, huecos vendibles
- Capa D Riesgo: conflictos, overbookings, tripulación faltante, pagos pendientes, maintenance cercano

## TIPOS DE BLOQUES — NO TODO ES RESERVA

El sistema debe modelar 5 tipos de bloques:
1. Booking — reserva real (bloque sólido)
2. Hold — bloqueo temporal pendiente de pago (borde dashed)
3. Maintenance — reparación, inspección, limpieza (patrón sutil + icono wrench)
4. Internal Block — uso interno, traslado, fotos (tono neutral + icono shield)
5. Buffer — tiempo protegido antes/después de salida (bloque fino translúcido)

Cada tipo tiene comportamiento visual y operativo distinto. Un hueco "libre" no siempre es vendible.

## CHECKPOINT DE DECISIÓN INICIAL (OBLIGATORIO ANTES DE CÓDIGO)

Responde estas 8 preguntas antes de escribir una línea:

1. ¿El calendario vive en /dashboard.html o hay que crear ruta separada (ej: /fleet.html)?
2. ¿Cuántos barcos activos hay en la tabla boats? Lista nombres exactos y columna de identificación.
3. ¿La data de capitán y stew vive en bookings directamente (campos captain_name, stew_name) o en tabla separada (crew_assignments)?
4. ¿Existe tabla de holds, maintenance, blackout_dates o similar? Si no, hay que crearlas como parte del sprint.
5. ¿Existe tabla o campo para buffers entre reservas? Si no, ¿cuál es la política default (30 min, 1h, 2h)?
6. ¿Hay conflictos de overbooking históricos en data? Query: SELECT boat_type, booking_date, COUNT(*) FROM bookings GROUP BY boat_type, booking_date HAVING COUNT(*) > 1
7. ¿Existen categorías de paquete/tipo de tour en data, o todas las reservas son genéricas?
8. ¿La columna boat_type tiene valores consistentes? (SELECT DISTINCT boat_type FROM bookings)

Con esas 8 respuestas adaptamos el plan. Si faltan tablas (holds, maintenance, crew), el sprint incluye migraciones para crearlas.

## LAS 4 VISTAS DEL SISTEMA

### VISTA 1 — FLEET TIMELINE (default)

La vista maestra. Propósito: control semanal de toda la flota.

Estructura:
- Eje Y: cada barco una fila
- Eje X: tiempo horizontal
- Zoom: 3d / 7d (default) / 14d / 30d
- Sticky left rail (140px) con info del barco
- Sticky top con KPIs del rango

Sub-modos del Timeline (conmutador secundario):
- Bookings (default) — reservas + holds + maintenance
- Operations — añade capitán, stew, buffers, pickup/boarding/departure
- Revenue — chips de revenue por bloque + intensidad por barco
- Utilization — resalta % ocupación por barco + gaps vendibles

### VISTA 2 — WEEKLY GRID

Plan táctico diario de UN barco.
- Selector de barco arriba
- Horas 07:00-22:00, slots de 30 min
- Bloques verticales con altura proporcional a duración
- Línea horizontal de "ahora" en tiempo real
- Filtros: por capitán, por estado, toggle show buffers, toggle show maintenance

### VISTA 3 — MONTH

Vista ejecutiva y de planeación.
Cada celda de día muestra:
- Número del día grande
- Revenue del día (mono, destacado)
- Hasta 3 bookings como píldoras (color del barco)
- "+N más" clickeable
- Mini dots por barco activo
- Icono alert si hay incidencia
Hover/click abre popover con resumen del día.

### VISTA 4 — LIST

Vista operacional-administrativa.
- Tabla densa con sort por cualquier columna
- Filtros guardables (saved views)
- Bulk actions: assign captain, confirm, cancel, export, move
- Densidad toggle (32/40/56px row)
- Export CSV/PDF

## REGLA MAESTRA DE COLOR

Cada bloque de reserva combina 3 señales sin colisionar:
1. Identidad de barco → borde izquierdo de 3px en --boat-*
2. Estado de la reserva → fondo del bloque al 15% opacity en --status-*
3. Alerta operativa → badge en esquina superior derecha con color --alert-*, solo si hay warning/critical

De un vistazo ves: QUÉ barco (borde), EN QUÉ estado (fondo), SI hay riesgo (badge).

## LEFT RAIL POR BARCO — MINI CONSOLA

Cada fila de barco muestra:
● CRANCHI            ← dot color barco
72% utilized
$6,800 this week
Next: Today 4:00 PM
Status: Ready

Estados del barco:
- Ready (verde): sin reservas ahora, disponible
- Booked (azul): reserva en curso
- Turnaround (ámbar): entre reservas, en buffer
- Maintenance (rojo): bloqueo técnico activo
- Out (gris): fuera de servicio

Click en la rail → abre detalle del barco con toda su data.

## OPERATIONS ALERTS PANEL

Panel plegable con feed de alertas rankeadas:

1. No captain assigned (critical si <24h)
2. No stew assigned (warning)
3. Payment pending (critical si <24h, warning si <72h)
4. Overlap detected (critical)
5. Double-assigned crew (critical)
6. Buffer too short (warning <30min, critical <15min)
7. Maintenance conflict (critical)
8. Missing waiver/docs (warning si <12h)
9. Back-to-back risky turnaround (warning)
10. Weather review pending (info)

Cada alerta:
- Click → resalta bloque + abre drawer
- Action inline: "Asignar capitán" / "Marcar pagado" / "Resolver"
- Severity dot (ámbar/rojo)
- Timestamp relativo

## OPEN GAP DETECTION (diferenciador premium)

Sistema detecta automáticamente huecos monetizables:
- Gaps de 2h+ entre bookings del mismo barco
- Gaps compatibles con sunset (3-5 PM)
- Same-day sellable windows
- Días completos sin reserva

Visualización:
- Overlay punteado sobre el hueco en Timeline
- Chip "4h gap" en el centro
- Click → acciones: Offer sunset package / Offer short charter / Mark not sellable / Reserve for maintenance / Share on channels

## CONTROL STRIP "TODAY"

Banda operacional superior, siempre visible:
⏰ Next departure in 42m · 🧑 2 unassigned crew · 💳 1 payment pending · 🛥 Cranchi free from 6-9 PM · 🔧 Viking Princess in maintenance

Actualización cada 60s.

## INTERACCIONES CRÍTICAS

Timeline:
- Click: abrir drawer

- Drag: mover reserva (con preview de impacto)
- Resize (borde derecho): ajustar duración

Reglas inviolables:
- Ningún cambio silencioso. Siempre preview antes de guardar.
- Mostrar impacto: Crew conflict / Payment implications / Maintenance conflict / Lost revenue risk / Cliente notification required

## ARQUITECTURA DE DATOS

Si tablas no existen, crear como parte del sprint:

ALTER TABLE bookings ADD COLUMN IF NOT EXISTS captain_name TEXT;
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS stew_name TEXT;
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS start_time TEXT;
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS duration_hours NUMERIC(4,2);
ALTER TABLE bookings ADD COLUMN IF NOT EXISTS payment_status TEXT 
  CHECK (payment_status IN ('paid','partial','pending','refunded'));

CREATE TABLE IF NOT EXISTS holds (
  id TEXT PRIMARY KEY,
  boat_type TEXT NOT NULL,
  start_datetime TIMESTAMPTZ NOT NULL,
  end_datetime TIMESTAMPTZ NOT NULL,
  reason TEXT,
  expires_at TIMESTAMPTZ,
  created_by TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS maintenance_blocks (
  id TEXT PRIMARY KEY,
  boat_type TEXT NOT NULL,
  start_datetime TIMESTAMPTZ NOT NULL,
  end_datetime TIMESTAMPTZ NOT NULL,
  maintenance_type TEXT,
  severity TEXT CHECK (severity IN ('soft','hard')),
  workshop TEXT,
  status TEXT CHECK (status IN ('planned','in-progress','waiting-parts','completed','delayed')),
  notes TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS fleet_config (
  boat_type TEXT PRIMARY KEY,
  display_color TEXT,
  short_label TEXT,
  is_active BOOLEAN DEFAULT true
);

CREATE TABLE IF NOT EXISTS operations_alerts (
  id TEXT PRIMARY KEY,
  alert_type TEXT NOT NULL,
  severity TEXT CHECK (severity IN ('info','warning','critical')),
  booking_id TEXT REFERENCES bookings(id),
  message TEXT,
  detected_at TIMESTAMPTZ DEFAULT NOW(),
  resolved_at TIMESTAMPTZ,
  resolved_by TEXT
);

## REGLAS DE ORO (no negociables)

1. Ninguna feature antes de que la Fase 1 esté sólida. El Timeline es el corazón.
2. Color tiene significado, no decoración. Barco=identidad, Estado=fondo, Alerta=badge.
3. Densidad sobre espaciado. Operaciones, no marketing.
4. Nunca ocultar información crítica en hover.
5. Conflictos gritan visualmente. Overbooking y solapamientos no se pasan por alto.
6. Cero cambios silenciosos. Drag & drop siempre con preview + confirmación.
7. Compresión de texto automática. Bloque nunca rompe layout.
8. Performance desde día 1. Virtualización, memoización, prefetch.
9. Consistencia con NBIC. Tokens, fuentes, componentes reutilizados.
10. Todo dato operativo es clickeable y lleva al detalle.
