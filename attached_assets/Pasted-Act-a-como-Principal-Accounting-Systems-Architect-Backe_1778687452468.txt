Actúa como Principal Accounting Systems Architect, Backend Engineer y Product Engineer para gestion.nadakiexcursions.

PROBLEMA:
El Booking Reconciliation Wizard no permite registrar pagos parciales o múltiples abonos al capitán. Actualmente intenta registrar el pago al capitán como un único gasto cerrado, pero en la operación real puede ocurrir que el capitán reciba una parte en efectivo y luego otro pago por Zelle/banco/cash para completar su monto total.

CASO REAL:
Capitán Pablo:
- Servicio: 5 horas
- Tarifa: $50/hora
- Monto total debido: $250
- Primer abono: $114 en efectivo
- Saldo pendiente: $136
- Segundo abono: puede ser Zelle, banco o cash

OBJETIVO:
Implementar soporte completo para cuentas por pagar al capitán y pagos parciales múltiples.

==================================================
1. MODELO CONTABLE CORRECTO
==================================================

El pago al capitán debe tener dos niveles:

A) Obligación / costo total del servicio:
Dr 5010 Captain Labor Expense
Cr 2000 Accounts Payable

B) Pagos parciales al capitán:
Dr 2000 Accounts Payable
Cr 1015 Cash Clearing si pago es cash
Cr 1010 Wells Fargo Checking si pago es Zelle/bank
Cr selected account si otro método

IMPORTANTE:
No registrar cada abono como nuevo gasto si ya se reconoció el costo total.
Los abonos deben reducir Accounts Payable.

==================================================
4. BACKEND ENDPOINTS
==================================================

Crear endpoints:

POST /api/bookings/:id/captain-payable

Body:
{
  "captain_name": "Pablo",
  "service_hours": 5,
  "hourly_rate": 50,
  "notes": "Captain service for booking"
}

Acción:
- Crear obligación si no existe
- Crear asiento:
  Dr 5010 Captain Labor Expense
  Cr 2000 Accounts Payable
- total_due = service_hours * hourly_rate
- status = pending

No duplicar obligación si ya existe para ese capitán y booking.

POST /api/bookings/:id/captain-payable/:payable_id/payments

Body:
{
  "amount": 114,
  "payment_method": "cash",
  "payment_date": "2026-04-27",
  "notes": "Partial cash payment to captain"
}

Acción:
- Validar amount > 0
- Validar payable existe
- Crear asiento:
  Dr 2000 Accounts Payable
  Cr 1015 Cash Clearing si cash
  Cr 1010 Wells Fargo si zelle/bank
- Actualizar total_paid
- Actualizar balance_due
- Actualizar status:
  if total_paid = total_due → paid
  if total_paid < total_due → partially_paid
  if total_paid > total_due → overpaid

GET /api/bookings/:id/captain-payable

Debe devolver:
- total_due
- total_paid
- balance_due
- status
- payments list
- related transactions

==================================================
5. VALIDACIONES
==================================================

- No permitir pago parcial mayor que balance_due sin confirmación.
- Si pago excede total_due, marcar overpaid y pedir clasificación:
  - tip_authorized
  - payment_error
  - company_credit
  - manual_adjustment

- Si payment_method = cash:
  debe verificar Cash Clearing disponible o permitir balance negativo con alerta crítica.
- Si payment_method = zelle/bank:
  no debe afectar Cash Clearing.
- No permitir esto en booking legacy salvo prior period adjustment.
